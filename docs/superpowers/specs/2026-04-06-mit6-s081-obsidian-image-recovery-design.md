# MIT 6.S081 Obsidian Wiki 图片恢复与重绘设计

## 背景

当前 vault `/Users/qingcongyu/Documents/mit6.s081` 已经完成课程页面的导入和 wiki 化整理，但图片内容整体缺失。现状不是少量页面丢图，而是导入材料中保留了大量 `.gitbook/assets/...` 引用，却没有将对应图片资源落到 vault 中。

本次工作需要把图片问题从一次性修补改造成稳定的媒体处理流程。目标不是机械恢复所有原图，而是以 GitBook 原图为参考，尽量还原其信息结构，并把潦草手写图改造为适合 Obsidian 学习和 AI 检索的清晰版教学图。

## 现状审计

基于当前 vault 的审计结果：

- `material/mit6-s081-repo/` 中共有 180 个材料页
- 其中 159 个材料页包含图片引用
- 当前材料页中的图片引用总数约为 818
- vault 中当前不存在任何 `.png/.jpg/.webp/.svg` 图片资产文件
- GitBook 页面本身仍然存在图片节点，可解析出真实图片 URL

这说明问题的根源不是 GitBook 页面没图，而是当前生成器没有建立媒体抓取、媒体分类、正式资产生成和页面回写这几步。

## 目标

- 为当前 vault 建立可重跑的图片恢复与重绘流程
- 以 GitBook 图片为参考输入，尽量还原原课件的结构和教学重点
- 将难以辨认的手写图重绘为清晰版教学图
- 对代码截图、终端截图、GDB/汇编界面截图采用更稳妥的转写策略，避免错误重绘
- 在 Obsidian 中形成稳定的资产目录和稳定引用，确保以后重建 vault 时不会再次丢图

## 非目标

- 不追求对所有图片做逐像素还原
- 不把所有截图都强行转换成重绘图
- 不在第一阶段补充所有可能的图片说明文字和 alt 文本
- 不依赖人工逐张修图作为主流程

## 设计原则

### 原图是参考，不是默认成品

GitBook 原图主要承担“识别结构和语义”的作用。对于手写潦草图，最终呈现在 vault 中的应该是清晰重绘版，而不是直接搬运原图。

### 先分流，再生成

不是所有图片都适合重绘。必须先基于图片内容和上下文分类，再决定是重绘、保留、还是转写成 markdown 内容。

### 正式资产与参考资产分层

参考图、正式重绘图、截图转写内容不能混在一起。否则下一次重建时无法判断哪些内容可覆盖、哪些内容应保留。

### 页面中的引用必须稳定

正式笔记只能引用正式资产层，不直接引用 GitBook 外链，也不直接依赖 `material/` 中的原始相对路径。

## 资产结构

在 vault 中新增如下目录：

```text
/Users/qingcongyu/Documents/mit6.s081/
├── assets/
│   ├── gitbook-source/
│   ├── redraw/
│   └── transform/
└── visual-notes/
```

各目录职责如下：

- `assets/gitbook-source/`
  - 存放从 GitBook 实际抓取到的原始参考图
  - 仅作为参考输入，不作为默认学习成品
- `assets/redraw/`
  - 存放清晰重绘后的正式教学图
  - 这是 source 页面和 visual note 页面优先嵌入的图片层
- `assets/transform/`
  - 存放截图转写过程中需要的辅助资源，例如局部裁剪图或保留的高质量截图
- `visual-notes/`
  - 存放无法可靠重绘的图片位点对应的解释页、代码转写页、终端输出整理页

## 命名规范

所有图片位点按“页面 + 顺序号”稳定命名，不使用随机文件名。

示例：

- `assets/gitbook-source/lec08/8.2/fig-01-source.png`
- `assets/redraw/lec08/8.2/fig-01-redraw.png`
- `visual-notes/Lec08 8.2 Fig01 说明.md`

命名规则：

- lecture 目录名沿用课程编号，如 `lec08`
- 子页面目录沿用 lecture 内章节号，如 `8.2`
- 每个图片位点按该页面内的出现顺序编号，如 `fig-01`
- `source`、`redraw`、`transform` 后缀表示资产角色

这样可以保证：

- 同一页面的图片顺序稳定
- 重跑流程时可以精确定位到同一图片位点
- 后续人工补充不会因为源图 URL 变化而失去对应关系

## 图片分类模型

每个缺图位点都必须进入以下三类之一：

### 1. diagram-redraw

适用对象：

- 内存布局图
- 调用路径图
- 状态转换图
- 页表、进程、文件系统等结构示意图
- 具有明确对象、箭头、区域和标签的教学图

处理策略：

- 先抓 GitBook 参考图
- 结合图前后段落提取语义
- 生成信息结构尽量等价、文字更清晰、布局更整洁的教学图
- 正式页面引用 `assets/redraw/`

### 2. screenshot-preserve

适用对象：

- 本身已经足够清晰的图
- 有必要保持原始样貌的特定截图
- 不适合改写但也不需要重绘的少量图片

处理策略：

- 抓取原图
- 直接纳入正式资产或经过轻微清理后使用
- 页面优先嵌入保留版，不强制转成重绘图

### 3. screenshot-transform

适用对象：

- 代码截图
- 终端输出截图
- GDB 调试界面截图
- 汇编界面截图
- 含大量文本、窗口装饰、命令行环境信息的截图

处理策略：

- 不做假想式“重绘截图”
- 将关键信息转写成更稳定的 markdown 表达
- 例如代码块、callout、带解释的局部图、步骤说明
- 页面中嵌入 `visual-notes/` 对应说明页，或直接写回整理后的代码块

## 页面引用规则

source 页面和相关笔记中的图片位点统一按以下规则回写：

- 对 `diagram-redraw`：嵌入 `![[assets/redraw/...]]`
- 对 `screenshot-preserve`：嵌入保留后的正式图片资产
- 对 `screenshot-transform`：嵌入 `![[visual-notes/...#某个标题]]`，或直接写入整理后的代码块和 callout
- 对尚未完成处理的位点：写入明确占位 callout，说明参考图已抓取、正式版本待补

禁止继续保留如下形式作为最终引用：

- `![](<../.gitbook/assets/...>)`
- 外部 GitBook 图片 URL
- 无来源说明的临时图片路径

## 批处理流程

### 1. 缺图审计

扫描 vault 中所有 markdown，建立图片位点清单。每条记录至少包含：

- 所在笔记路径
- 对应 material 路径
- 原始 `.gitbook/assets/...` 引用
- 页面中的顺序号
- 图片前后文摘要
- 当前状态：`missing / source-fetched / redraw-done / transformed`

### 2. 参考图抓取

根据 source 页对应的 GitBook 页面，解析真实图片 URL 并下载到 `assets/gitbook-source/`。

同时记录：

- 抓取时间
- 原始页面 URL
- 图片顺序号
- 文件格式和尺寸

### 3. 自动分类

根据图片上下文和参考图特征做初步分类：

- 含代码字体、终端界面、大量文字密集区的，优先归入 `screenshot-transform`
- 含区域、箭头、方框、示意布局的，优先归入 `diagram-redraw`
- 清晰度足够且保留价值高的，归入 `screenshot-preserve`

分类结果允许后续人工调整，但第一轮必须足够稳定，支持批处理。

### 4. 正式内容生成

#### diagram-redraw

输入：

- GitBook 参考图
- 所在页面标题
- 图片前后文
- 图片在页面中的顺序和作用

输出：

- 一张清晰版教学图
- 尽量还原原图的对象关系、箭头方向、层次结构和标签语义
- 视觉风格统一、字迹清晰、适合 Obsidian 嵌入

#### screenshot-preserve

输入：

- 原始参考图

输出：

- 正式保留版图片，必要时做轻度整理

#### screenshot-transform

输入：

- 原始参考图
- 上下文

输出：

- 对应的 `visual-notes/` 页面
- 页面中包含代码块、callout、分步说明、必要时的局部图嵌入

### 5. 页面回写

将原先的 `.gitbook/assets/...` 缺图位点替换成正式内容，并更新相关 source 页面。

### 6. 日志记录

每次批处理完成后，向 `log.md` 追加：

- 本次处理了哪些 lecture / 页面
- 抓取原图数量
- 重绘完成数量
- 转写完成数量
- 保留原图数量
- 剩余待处理数量

## 批次策略

第一阶段不直接处理全部约 818 个位点，而是按 lecture 批次推进。

首批范围：

- `Lec01` 到 `Lec08`

原因：

- 可以先验证图片分类是否可靠
- 可以先验证“重绘图”和“截图转写页”的视觉风格是否合适
- 可以先验证 Obsidian 中的嵌入、索引和后续重建是否稳定

首批验证通过后，再逐步推广到后续 lecture。

## 工具与实现边界

### GitBook 页面处理

- 继续使用 GitBook 页面作为图片来源
- GitHub 仓库继续作为正文 markdown 的主要来源
- 图片流程需要新增“页面 HTML 解析和图片下载”能力

### 图像生成

- 仅对 `diagram-redraw` 使用图像模型生成清晰版教学图
- 生成提示词必须强调“结构尽量还原、表达更清晰”，避免无关装饰
- 不把代码截图、终端截图直接丢给图像模型做臆造重绘

### Obsidian 写回

- 正式生成的图片和 visual note 必须进入 vault 的稳定目录
- 生成器重跑时不得覆盖用户手工修订过的正式资产，除非明确要求刷新

## 风险与缓解

### 风险 1：参考图解析失败

缓解：

- 优先从 GitBook 页面解析图片 URL
- 解析失败时记录到待补清单，不静默跳过

### 风险 2：重绘图偏离原图

缓解：

- 只对结构图重绘
- 保持“原图参考 + 上下文摘要 + 版式约束”三要素输入
- 先从一小批页面试跑并人工抽查

### 风险 3：截图被错误分类为重绘图

缓解：

- 首轮分类偏保守，宁可归入 `screenshot-transform`
- 把高文本密度图优先排除出重绘队列

### 风险 4：未来重建覆盖人工成果

缓解：

- 参考资产和正式资产分层
- 只让页面引用正式资产层
- 在生成清单中记录资产状态和来源

## 验证标准

满足以下条件才算该流程成立：

- vault 中新增稳定的图片资产目录和 visual note 目录
- 首批 lecture 页面中的缺图位点不再悬空
- 对结构图，页面中出现清晰版教学图
- 对截图类图，页面中出现可读的转写内容或保留图
- `log.md` 能反映每次批处理的结果
- 生成器重跑后，正式页面仍保持正确引用，不回退到 `.gitbook/assets/...`
